# Issue作成スキル(テンプレート)

> このスキルは雛形です。`<your-org>/<repo>` やラベル名は自分の環境に合わせて
> 書き換えて使ってください。

**Issueを立てたら手順を全部やる**(ラベルだけ付けて終わらせない)。

## 1. 作成

```bash
gh issue create --repo <your-org>/<repo> \
  --title "<症状+発生条件を一行で>" --body-file <本文ファイル>
```

本文テンプレート:

```markdown
## 環境

<機体名、OS/ROSディストロ、ブランチ・コミット、関わるハードウェア>

## 症状と再現手順

<何が起きたか。再現手順は番号付き・コピペで動くコマンドで。再現率(毎回/たまに)も>

## 期待する動作と実際の動作

<expected vs actual を分けて。エラーは生ログを引用(要約だけにしない。
長ければ該当部+ログファイルの場所)>

## 影響

<これがあると何が困るか、頻度、回避策の有無(回避策があるかで優先度が判断できる)>

## 調査結果・原因の推定

<調査でわかったこと。事実と推測を明確に分ける
(例: 「13:56にサービス起動を確認(事実)」「電源断が原因と推定(推測)」)>

## 要望・修正案

<直してほしいこと(箇条書き)。案があれば具体的に>

## 依存・関連

<関連issue/PR、またがるリポジトリ、これにブロックされている作業>

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

## 2. 書き方の基準

- **良いIssueの基準**: 読んだ人がIssueだけで「再現 → 検証 → 直すかどうかの判断」まで
  できる自己完結性。書き手の頭の中の文脈を全部紙面に降ろす。未来の自分も「他の人」
- タイトルは「〜が調子悪い」ではなく「<条件>のとき<何>が<どうなる>」まで具体化
- 該当しないセクションは削ってよいが、**環境・再現・影響・依存の4つは省かない**

## 3. 作成後の登録

ラベル・Issue Type・Project登録など、自分のリポジトリの運用に合わせて漏れなく付ける:

```bash
gh api -X POST repos/<your-org>/<repo>/issues/<番号>/labels -f "labels[]=bug"
```

(組織でGitHub Projectsを使っている場合は、ここにProject登録手順を書き足す)
